# ADR-045：自动化测试延后至正式程序集阶段

- 状态：Accepted
- 日期：2026-09-20
- 关联：DES-033、ADR-026、ADR-032、ADR-039、ADR-042

## 背景

项目已经为 Army、Gate、Prop、Spawn、EventBus、Pool 和应用流程记录了大量可验证规则，自动化测试对这些确定性逻辑有长期价值。但当前工程明确不创建 `.asmdef`，所有正式脚本仍将先编入 Unity 默认程序集。

Unity Test Framework 的 EditMode/PlayMode 测试通常需要独立测试程序集。只新增测试 `.asmdef`、却让被测运行时代码继续留在默认 `Assembly-CSharp`，不能形成清晰且可持续的程序集引用边界；为了测试而提前拆分部分运行时程序集，也会违背 ADR-026 规定的统一工程化时机。

## 决策

1. 当前 MVP 代码生成与首轮集成阶段不创建任何 `.asmdef`，范围包括运行时、Luban 生成代码、Editor、EditMode 测试和 PlayMode 测试程序集。
2. 当前阶段不生成 Unity EditMode/PlayMode 自动测试代码。`05_Testing` 与各模块中的测试条目继续作为验收规格，但默认通过编译检查、结构化日志、Inspector 观察和可复现手工步骤执行。
3. 可计算规则仍优先写成无场景依赖的纯 C# 类；MonoBehaviour 只负责 Unity 生命周期、序列化绑定和表现适配。服务与协调器继续通过最小接口注入，使以后能够使用假实现测试，而不需要重写业务规则。
4. 每批代码交付必须说明已执行的编译或手工验证、未执行项和需要用户完成的资源绑定。没有实际验证的测试清单不得勾选，也不得描述为已通过。
5. 首轮至少验证启动、进入玩法、核心操作、Victory/GameOver、清理和重新开始；确定性规则按 `05_Testing` 清单逐项选择代表性边界用例手工复现。
6. 当 ADR-026 的粗粒度运行时程序集正式实施时，再同时创建测试程序集，并优先把 Army 分配与伤害、Gate/Prop 一次性结算、Spawn 游标与会话隔离、终局优先级、EventBus、Pool 和 Config 校验迁移为 EditMode 自动测试。需要场景、Pointer、Collider、Animator 或场景切换的用例再按收益选择 PlayMode 自动化。
7. 本决策只延后自动化执行方式，不降低既有验收标准，也不删除未来测试文件规划。

## 后果

- 首轮代码生成不会因为测试程序集而提前引入局部 `.asmdef` 或不完整的引用结构。
- 纯规则错误在当前阶段主要依赖小步实现、编译、代码审查和手工边界用例发现，回归效率低于自动化测试；因此每批修改范围必须保持小且可复现。
- 未来启用程序集时需要补回高价值自动测试，这属于正式程序集工程化的组成部分，而不是可永久跳过的工作。
- `05_Testing` 中的复选框表示验收项是否实际通过，不表示其必须由自动化测试执行。

## 验收标准

- 当前工程中不存在项目自建 `.asmdef` 或 Unity 自动化测试脚本。
- 代码目录和命名空间仍按未来 Contracts、Foundation、Gameplay、Presentation、Composition 边界组织。
- 纯计算和状态转换不依赖场景搜索、静态全局状态或不可替换的 Unity 生命周期。
- 每轮工程修改均报告编译结果、已执行的手工验证和未验证项。
- 正式程序集实施计划同时包含运行时程序集、EditMode 测试程序集、必要的 PlayMode 测试程序集及其引用验证。
